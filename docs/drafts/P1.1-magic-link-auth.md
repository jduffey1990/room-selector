# P1.1 magic-link email verification

**Status: DECIDED 2026-07-28 — owner chose Option A** (codes gate access,
auth binds identity at submission). Not yet implemented; the Option A
sketch below is the implementation reference. Results notification at
finalization ships in the same pass via Brevo's HTTP API (see CLAUDE.md
P1.2) — not the deprecated Trigger Email extension.

## The problem

Anyone can submit as any email address, or as five addresses. Impersonation
and ballot-stuffing both work, which undercuts the entire fairness claim:
an envy-free allocation over forged ballots is fairly allocating fiction.
P1.2's mutual bed-sharing confirmation narrows couple forgery but does not
verify that either address belongs to the person typing it.

## The decision the owner has to make

How does email verification interact with the existing code-based flow?
Three coherent options:

### Option A — codes gate access, auth binds identity (recommended)

Trip codes keep doing what they do today (find the trip, gate reads).
Verification is required only at the moment of submission: the participant
signs in with a Firebase Auth email link, and `submitPreferences` takes the
email from `request.auth.token.email` instead of the request body.

- Keeps the product's no-accounts charm: a participant still needs nothing
  but the shared link until the moment they submit.
- Smallest change surface: one client flow, one callable check. Admin flow,
  rules, and the allocator are untouched.
- Builds exactly the channel P4 needs (verified addresses to email results
  to at finalization — the one non-optional notification).

### Option B — auth replaces codes

Accounts plus per-trip membership lists; codes become invitations that
attach a user to a trip.

- Strictly more machinery: user records, membership documents, revocation.
- Kills "no user accounts is the product's charm and its whole threat
  model" (ARCHITECTURE.md). Not recommended, listed for completeness.

### Option C — verify-at-submit without Firebase Auth sessions

Submission is written in a `pending` state; a signed one-time link goes to
the address; clicking it flips the submission to `verified`. Unverified
submissions are excluded from allocation.

- No auth session, so nothing persists between trips.
- More moving parts we own ourselves (token signing, expiry, resend); the
  failure modes (submitted-but-never-clicked) land on the organizer right
  before allocation, which is the worst possible time.

## Recommendation

Option A. It is the smallest change that makes the acceptance test pass
("a submission from an unverified address is rejected"), it reuses
Firebase's tested link flow instead of a hand-rolled one, and it produces
the verified address list P4 needs.

## Sketch for Option A (not implemented)

Client (`SubmissionForm`):

1. Participant fills the form as today. On submit, if not signed in:
   `sendSignInLinkToEmail(auth, email, {url: current trip URL, handleCodeInApp: true})`,
   stash the form state in `localStorage`, show "Selecta-bot has posted you
   a verification link" (plain copy about what to do; no flourish beyond
   that — this is an integrity step).
2. The link returns to the trip URL; `isSignInWithEmailLink` completes
   sign-in, the stashed form state is restored and submitted automatically.
3. Signed-in participants (repeat submitters, second device) skip step 1.

Functions:

- `submitPreferences`: require `request.auth`; take the submission email
  from `request.auth.token.email`, drop the body field. Reject mismatched
  `partnerEmail === own email` as today. Partner declarations remain
  unverified strings until the partner submits (their own submission is
  what verifies them, so mutual confirmation composes cleanly with auth).
- Other callables unchanged. Trip creation stays code-based (that is
  P1.3's App Check problem, not an auth problem).

Config/ops:

- Enable Email Link sign-in in Firebase Auth; add the hosting domains to
  authorized domains. No new secrets.
- The seed script writes submissions with the Admin SDK and is unaffected,
  but the e2e harness cannot click an emailed link: give it a
  `FIREBASE_AUTH_EMULATOR_HOST` path for local runs, and for production
  e2e either a test-only App Check debug token + allowlisted test domain,
  or keep one `[demo]` trip writable via a temporary env-gated bypass in
  submitPreferences. That choice can wait until this ships.

## Interactions worth flagging

- **Couples (P1.2):** unchanged. A couple still requires both partners to
  submit — and now both are verified. The partner field just names an
  address; it never creates identity.
- **Admin:** admin code stays the credential. Verifying organizers is a
  separate, later question (they created the trip; there is nothing to
  impersonate yet).
- **Results (P4):** `getResults` can later accept auth instead of a code
  for participants, but that is additive, not required.
- **Migration:** existing trips have unverified submissions. Enforce auth
  only for new submissions; do not retroactively invalidate.

## Acceptance (from CLAUDE.md)

A submission from an unverified address is rejected. Under Option A this is
structural: `submitPreferences` refuses calls without `request.auth`, and
the email is read from the verified token, so there is no unverified path
to reject — it cannot be expressed.
